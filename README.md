# RED vs BLUE

Игра для команды: реальные общие голоса в Firebase Realtime Database, участники на телефонах, пульт ведущего и отдельный экран для проектора. React + TypeScript + Vite + Tailwind CSS; собственный сервер не нужен. Интерфейс полностью на русском.

**Без настроенного Firebase игра не запустится.** Приложение честно показывает экран настройки; демонстрационные голоса и локальная имитация отсутствуют. Примерные вопросы записываются в Firebase при создании игры и редактируются ведущим.

## 1. Подготовка компьютера

Установите Node.js 22 LTS, Git и Java 21 (Java нужна только для локальных тестов правил). Откройте терминал в папке проекта, где находится `package.json`:

```sh
npm install
cp .env.example .env
```

Windows PowerShell: вместо `cp` можно использовать `Copy-Item .env.example .env`.

## 2. Создание Firebase

1. Откройте [Firebase Console](https://console.firebase.google.com/), нажмите **Add project / Создать проект**. Для этой игры достаточно плана Spark, подключать платёжную карту не требуется. Google Analytics можно не включать.
2. В **Project settings → General → Your apps** добавьте веб-приложение (значок `</>`), задайте имя. Firebase Hosting подключать не нужно.
3. Скопируйте значения `apiKey`, `authDomain`, `projectId`, `appId` из конфигурации SDK в соответствующие переменные `.env`:

```dotenv
VITE_FIREBASE_API_KEY=значение_apiKey
VITE_FIREBASE_AUTH_DOMAIN=ваш-проект.firebaseapp.com
VITE_FIREBASE_DATABASE_URL=https://точный-адрес-базы-из-консоли
VITE_FIREBASE_PROJECT_ID=идентификатор-проекта
VITE_FIREBASE_APP_ID=значение_appId
```

4. Откройте **Build → Realtime Database → Create Database**, выберите регион поближе к мероприятию и **Locked mode / Заблокированный режим**. Не выбирайте Cloud Firestore — это другой продукт.
5. Скопируйте URL созданной базы с вкладки **Data** в `VITE_FIREBASE_DATABASE_URL`. Региональные адреса могут оканчиваться на `firebasedatabase.app`, не придумывайте URL самостоятельно.
6. В **Build → Authentication → Get started → Sign-in method** включите **Anonymous** и **Email/Password**. Вход по email-ссылке не нужен.
7. В **Authentication → Settings → Authorized domains** добавьте `localhost` и домен GitHub Pages, например `username.github.io` (без `https://` и пути). Для пользовательского домена добавьте и его.

Эти `VITE_` значения попадут в JS-сборку. Они идентифицируют публичное Firebase-приложение и не являются административными секретами. За доступ отвечают Authentication и правила базы. **Никогда не добавляйте service-account JSON, приватный ключ, пароль ведущего или Firebase Admin SDK в клиент или репозиторий.** [Документация о Firebase API keys](https://firebase.google.com/docs/projects/api-keys).

## 3. Аккаунт ведущего и список администраторов

1. В **Authentication → Users → Add user** создайте пользователя с email и надёжным паролем.
2. Скопируйте его **User UID**.
3. В **Realtime Database → Data** добавьте узел `admins`, в нём ключ, равный UID пользователя, со значением **boolean `true`**, не строкой `"true"`:

```json
{"admins":{"UID_ИЗ_AUTHENTICATION":true}}
```

Добавляйте узел, а не импортируйте этот объект поверх всей существующей базы. Для ещё одного ведущего добавьте ещё один UID. Для отзыва доступа удалите UID. Все включённые в список ведущие имеют доступ ко всем играм проекта. Администраторы Firebase Console также управляют базой через IAM.

Клиент не может изменять `admins`; allowlist читается только для собственного UID. Email/password без присутствия UID в allowlist не даёт права управлять игрой.

## 4. Публикация правил безопасности

Простой вариант: **Realtime Database → Rules**, замените содержимое на весь файл `database.rules.json`, затем **Publish**. Не оставляйте тестовые правила `".read": true, ".write": true`.

Вариант через CLI (входит в зависимости):

```sh
npx firebase login
npx firebase deploy --only database --project ВАШ_PROJECT_ID
```

Это публикует правила в выбранный Firebase-проект; GitHub Actions ниже публикует только frontend, правила автоматически не меняет.

## 5. Локальный запуск

```sh
npm run dev
```

Откройте URL Vite (обычно `http://127.0.0.1:5173`). Маршруты:

- `/#/play` — вход участника;
- `/#/admin` — вход и пульт ведущего;
- `/#/screen?game=ABC234` — проектор;
- `/#/play?game=ABC234` — прямая ссылка участнику.

Если поменяли `.env`, перезапустите Vite. Локальный интерфейс подключается к настоящему Firebase из `.env`; тесты используют отдельный emulator project `demo-*`. Для участника и ведущего используйте разные профили браузера: Firebase Auth разделяет сессию между вкладками одного профиля.

```sh
npm run build
npm test
npm run test:rules
npm run test:load
```

`build` проверяет TypeScript и создаёт `dist/`. `test:rules` и `test:load` автоматически запускают и останавливают локальный Realtime Database emulator на порту 9000. Первый запуск скачивает Java emulator и требует интернета. При занятом порте остановите другой emulator. Тесты используют подставленные Firebase Auth claims только в emulator; в production используется настоящий Firebase Auth SDK.

## 6. GitHub Pages

1. Создайте пустой GitHub-репозиторий, например `red-vs-blue`. Загружайте **содержимое этой папки**, чтобы `package.json` и `.github` были в корне репозитория.
2. В **Settings → Secrets and variables → Actions → Variables** добавьте все пять `VITE_FIREBASE_*` переменных с теми же значениями, что в `.env`. Это публичная конфигурация, допустимы repository variables. Не загружайте сам `.env`.
3. В **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**.
4. Если вы ещё не используете Git в этой папке:

```sh
git init -b main
git add .
git commit -m "Build RED vs BLUE multiplayer game"
git remote add origin https://github.com/USERNAME/red-vs-blue.git
git push -u origin main
```

Замените USERNAME своим именем. Для доступа к GitHub используйте поддерживаемый GitHub способ входа (GitHub CLI, credential manager или SSH), не пароль аккаунта в URL.

5. Дождитесь зелёного workflow **Проверка и публикация** во вкладке Actions. Он устанавливает зависимости через lockfile, запускает unit/rules tests, собирает приложение и публикует `dist`.
6. Откройте `https://USERNAME.github.io/red-vs-blue/#/admin`. При изменении Firebase variables повторно запустите workflow: они встраиваются во время сборки.

Vite использует относительный `base: './'`, а маршруты находятся после `#`. Поэтому и корень домена, и путь репозитория работают без серверных rewrite/404 hacks. Прямой путь `/admin` без `#` не поддерживается GitHub Pages. QR-код строится из фактического origin и pathname.

## 7. Первая игра

1. Ведущий входит на `#/admin` с созданным email/password. Нажимает **Создать игру**. Запишите код: по нему можно открыть пульт после перезагрузки или на другом устройстве.
2. Отредактируйте, удалите, добавьте и переставьте вопросы. У каждого вопроса есть текст, красный и синий ответы. Редактирование разрешено только в ожидании, что исключает изменение вопроса во время голосования.
3. Откройте **Экран для проектора** и разверните окно на весь экран средствами браузера. Перед стартом там видны QR-код и код игры.
4. Участники сканируют QR-код либо вводят код на `#/play`, затем никнейм. UID создаётся Anonymous Authentication и сохраняется Firebase в браузере. Никнейм не является паролем.
5. Сравните показатели **Участников всего**, **Сейчас в сети** и **Голосов в раунде**. Одна личность в нескольких вкладках считается одним подключённым участником.
6. Выберите вопрос и нажмите **Начать голосование**. На всех телефонах появятся ответы. Подтверждение появляется только после принятия записи сервером, а не сразу после касания.
7. Нажмите **Закрыть голосование**: запоздавшие записи отклоняются правилами. Затем **Показать результаты**: все клиенты загружают реальные голоса и рассчитывают одинаковые проценты.
8. Выберите следующий вопрос и откройте голосование. Автоматического перехода по таймеру нет.
9. Нажмите **Завершить игру**. Для повторной игры нажмите **Сбросить игру** и подтвердите очистку: голоса удаляются атомарно с возвратом в ожидание, вопросы и участники сохраняются. Для нового списка участников создайте новую игру.

Повторное открытие любого вопроса — новый раунд с новым уникальным ID, в котором снова можно проголосовать. Во время одного раунда изменить голос нельзя.

## Архитектура и целостность

```
admins/{uid}: true                      # allowlist, только Console/IAM пишет
 games/{code}/state                     # фаза, уникальный roundId, снимок вопроса
 games/{code}/questions/{questionId}     # редактируемый сценарий
 games/{code}/participants/{uid}/name    # неизменяемая регистрация
 games/{code}/presence/{uid}/{tabId}     # независимые соединения
 games/{code}/votes/{roundId}/{uid}      # red | blue, одна запись на раунд
 games/{code}/tally                     # публичное общее число, без разбивки
```

`roundId` — ID экземпляра вопроса; снимок вопроса содержит исходный `question.id`. Отдельный ID раунда предотвращает попадание задержавшегося голоса в повторно открытый вопрос или новую игру после сброса. Состояние и текст активного вопроса приходят одной записью: нельзя смешать новую фазу и старый текст из отдельных подписок.

Фазы: `waiting → question_open → voting_closed → results_revealed → question_open … → finished`. Ведущий может закончить игру из любой фазы. Переходы в UI проверяются и записываются транзакцией с проверкой текущих phase/roundId, чтобы два пульта не применили устаревшую команду. Правила доверяют авторизованным администраторам управлять состоянием; участники не могут изменять его никаким API-запросом.

Голос создаётся `runTransaction(..., {applyLocally:false})`; существующий голос прерывает повторную транзакцию. Правила независимо запрещают overwrite/delete, чужой UID, несуществующего участника, неправильное значение, закрытый и устаревший раунд. Нет клиентского admin secret. LocalStorage не хранит игровое состояние; браузерное persistence используется только Firebase Auth для идентичности.

Участник слушает состояние, свой профиль, свой голос и `.info/connected`. До раскрытия никто, кроме администраторов, не может прочитать весь список голосов или чужой голос. После раскрытия клиенты читают голосование текущего раунда; проценты вычисляются общей чистой функцией (синий = 100 − округлённый красный; при нуле голосов оба 0%). UID голосующих после раскрытия видны авторизованным клиентам, но список никнеймов доступен только ведущему.

Только пульт слушает все голоса во время голосования. Он публикует с задержкой 200 мс общее число `tally` для проектора без красно-синей разбивки. Это информационный счётчик: если все пульты закрыты, он не обновляется до повторного подключения ведущего. Итоговые результаты всегда вычисляются из самих голосов, никогда из `tally`. Все подписки очищаются при смене маршрута/раунда.

Присутствие: `.info/connected` → сначала регистрация `onDisconnect().remove()`, затем запись уникального соединения вкладки. При reconnect создаётся новое соединение. Разрыв сети может определяться сервером с задержкой; зарегистрированный участник остаётся в базе. При отсутствии сети голосовать нельзя; уже отправленная операция может ждать сервера, но не показывается успешной до подтверждения. После reconnect SDK синхронизирует текущее состояние. Поздняя запись проверяется на сервере ещё раз.

## Ограничения и подготовка мероприятия

- Один голос гарантирован **на Firebase UID на раунд**, а не на физического человека. Другой браузер, устройство, очистка данных или новая анонимная учётная запись позволяют получить другой UID. Код игры — приглашение, не секрет высокой энтропии и не защита от нежелательных участников. Не публикуйте код заранее в открытом доступе. Для строгого контроля нужны персональные приглашения и иной процесс регистрации.
- Spark Realtime Database допускает **100 одновременных соединений**, включая дополнительные вкладки, ведущего и проектор. 60 телефонов + 1 пульт + 1 проектор помещаются в этот лимит; это не обещание доступности конкретной сети. [Актуальные лимиты](https://firebase.google.com/docs/database/usage/limits).
- Spark также имеет ограничения хранения/трафика (проверяйте [тарифы](https://firebase.google.com/pricing) и Usage в Console). SDK, TLS, повторы и результаты создают трафик сверх размера JSON. Контролируйте накопленные игры и удаляйте старые через Console после мероприятия; не держите ненужные вкладки открытыми.
- Firebase Auth ограничивает частоту создания новых аккаунтов с одного IP. На общей Wi-Fi сети заранее проверьте регистрацию 60 телефонов. Не отключайте защиту и не создавайте сотни тестовых анонимных аккаунтов в production. [Auth limits](https://firebase.google.com/docs/auth/limits).
- Для входа администратора нужно интернет-соединение; offline voting намеренно не поддерживается. В iOS приватном режиме/после очистки данных стабильность UID между сессиями не гарантируется.
- Вопросы, профили и голоса хранятся до ручного удаления/сброса. После раскрытия участник может сохранить скачанные результаты: последующее закрытие прав не удаляет уже скачанную информацию.

## Тестирование и нагрузочная репетиция

Unit tests проверяют подсчёт, нулевые результаты, округление и разрешённые переходы. Rules tests используют реальные RTDB Security Rules в Firebase Emulator Suite: чужие права, overwrite/delete, дубликаты при гонке транзакций, закрытие раунда, видимость, присутствие, reconnect, reset. `test:load` создаёт **60 независимых SDK-клиентов** в emulator, подписывает их на состояние, регистрирует присутствие, одновременно пишет голоса, проверяет 24/36, доставку раскрытия всем 60 и удаление присутствия при отключении.

Результат локального прогона записан в `TESTING.md`. Emulator test не проверяет production Firebase Auth, мобильные браузеры, сеть площадки, TLS, бесплатные квоты или эксплуатационную надёжность 60 телефонов.

Ручной план перед мероприятием:

1. На отдельном тестовом Firebase-проекте разверните правила и frontend. Подключите 60 реальных телефонов (включая Safari iOS и Chrome Android), один пульт и проектор к сети площадки. Используйте по одной вкладке на телефон.
2. Зарегистрируйте участников; проверьте 60 регистраций и 60 подключённых UID. Отдельно откройте вторую вкладку на одном телефоне — счётчик людей не должен вырасти.
3. Откройте вопрос, распределите 24 красных / 36 синих. Нажмите одновременно; засеките время подтверждения и внесите p50/p95/max, ошибки и число подтверждённых голосов в журнал.
4. Повторно нажимайте, перезагрузите 10 устройств и попробуйте голосовать второй раз: итог остаётся 60. Проверьте восстановление текущего состояния без повторного ввода ника.
5. На 5 телефонах отключите сеть до ответа, на других — в момент отправки. Закройте голосование; восстановите сеть. Ни один голос, не принятый до закрытия, не должен появиться в результате.
6. Проверьте отсутствие чужих голосов в DevTools/API до раскрытия. После раскрытия на всех устройствах должно быть одинаковое 40% / 60% для успешного полного раунда.
7. Проведите 10 последовательных вопросов, в том числе раунд без голосов, завершение и сброс. Проверьте задержанные голоса из старого раунда. Закройте/откройте пульт; текущее состояние должно сохраниться.
8. Проверьте потерю сети проектора, уход мобильного браузера в фон, смену Wi-Fi на мобильную сеть. После восстановления проверьте актуальный вопрос и presence.
9. Запишите фактическое количество соединений, трафик и ошибки из Firebase Usage, модель/ОС устройств, качество Wi-Fi и задержки. При ошибках устраните причину и повторите репетицию. Не объявляйте production-нагрузку проверенной по одному emulator test.

### Необязательный локальный режим разработки с emulators

Для самостоятельной разработки можно подключить браузер к настоящим локальным Firebase emulators: в `.env.local` укажите все пять Firebase-полей с demo-проектом `demo-red-blue` (API key `demo-key`, app ID `demo-app`, auth domain `demo-red-blue.firebaseapp.com`, database URL `https://demo-red-blue-default-rtdb.firebaseio.com`) и `VITE_USE_EMULATORS=true`. В одном терминале запустите `npx firebase emulators:start --project demo-red-blue --only auth,database`, во втором — `npm run dev`. Auth работает на 9099, RTDB на 9000. Режим включается только при `import.meta.env.DEV`; production build не подключается к emulator. Не используйте demo-конфигурацию при публикации. Для автоматических тестов `.env` вообще не требуется.
