# RED vs BLUE

Игра для команды: реальные общие голоса в Firebase Realtime Database, участники на телефонах, пульт ведущего и отдельный экран для проектора. React + TypeScript + Vite + Tailwind CSS; собственный сервер не нужен. Интерфейс полностью на русском.

**Без настроенного Firebase игра не запустится.** Приложение честно показывает экран настройки; демонстрационные голоса и локальная имитация отсутствуют. Примерные вопросы записываются в Firebase при создании игры и редактируются ведущим.

**Для обновления уже опубликованной игры сначала прочитайте [MIGRATION.md](MIGRATION.md).** Новые правила и frontend необходимо выпускать согласованно.

## 1. Подготовка компьютера

Установите Node.js 22 LTS, Git и Java 21 (Java нужна только для локальных тестов правил). Откройте терминал в папке проекта, где находится `package.json`:

```sh
npm install
cp .env.example .env
```

Windows PowerShell: вместо `cp` можно использовать `Copy-Item .env.example .env`.

## 2. Создание Firebase

1. Откройте [Firebase Console](https://console.firebase.google.com/), нажмите **Add project / Создать проект**. Для этой игры достаточно плана Spark, подключать платёжную карту не требуется. Google Analytics можно не включать.
2. В **Project settings → General → Your apps** добавьте веб-приложение (значок `</>`), задайте имя. Firebase Hosting подключать не нужно.
3. Скопируйте значения `apiKey`, `authDomain`, `projectId`, `appId` из конфигурации SDK в соответствующие переменные `.env`:

```dotenv
VITE_FIREBASE_API_KEY=значение_apiKey
VITE_FIREBASE_AUTH_DOMAIN=ваш-проект.firebaseapp.com
VITE_FIREBASE_DATABASE_URL=https://точный-адрес-базы-из-консоли
VITE_FIREBASE_PROJECT_ID=идентификатор-проекта
VITE_FIREBASE_APP_ID=значение_appId
```

4. Откройте **Build → Realtime Database → Create Database**, выберите регион поближе к мероприятию и **Locked mode / Заблокированный режим**. Не выбирайте Cloud Firestore — это другой продукт.
5. Скопируйте URL созданной базы с вкладки **Data** в `VITE_FIREBASE_DATABASE_URL`. Региональные адреса могут оканчиваться на `firebasedatabase.app`, не придумывайте URL самостоятельно.
6. В **Build → Authentication → Get started → Sign-in method** включите **Anonymous** и **Email/Password**. Вход по email-ссылке не нужен.
7. В **Authentication → Settings → Authorized domains** добавьте `localhost` и домен GitHub Pages, например `username.github.io` (без `https://` и пути). Для пользовательского домена добавьте и его.

Эти `VITE_` значения попадут в JS-сборку. Они идентифицируют публичное Firebase-приложение и не являются административными секретами. За доступ отвечают Authentication и правила базы. **Никогда не добавляйте service-account JSON, приватный ключ, пароль ведущего или Firebase Admin SDK в клиент или репозиторий.** [Документация о Firebase API keys](https://firebase.google.com/docs/projects/api-keys).

## 3. Аккаунт ведущего и список администраторов

1. В **Authentication → Users → Add user** создайте пользователя с email и надёжным паролем.
2. Скопируйте его **User UID**.
3. В **Realtime Database → Data** добавьте узел `admins`, в нём ключ, равный UID пользователя, со значением **boolean `true`**, не строкой `"true"`:

```json
{"admins":{"UID_ИЗ_AUTHENTICATION":true}}
```

Добавляйте узел, а не импортируйте этот объект поверх всей существующей базы. Для ещё одного ведущего добавьте ещё один UID. Для отзыва доступа удалите UID. Все включённые в список ведущие имеют доступ ко всем играм проекта. Администраторы Firebase Console также управляют базой через IAM.

Клиент не может изменять `admins`; allowlist читается только для собственного UID. Email/password без присутствия UID в allowlist не даёт права управлять игрой.

## 4. Публикация правил безопасности

Простой вариант: **Realtime Database → Rules**, замените содержимое на весь файл `database.rules.json`, затем **Publish**. Не оставляйте тестовые правила `".read": true, ".write": true`.

Вариант через CLI (входит в зависимости):

```sh
npx firebase login
npx firebase deploy --only database --project ВАШ_PROJECT_ID
```

Это публикует правила в выбранный Firebase-проект; GitHub Actions ниже публикует только frontend, правила автоматически не меняет.

## 5. Локальный запуск

```sh
npm run dev
```

Откройте URL Vite (обычно `http://127.0.0.1:5173`). Маршруты:

- `/#/play` — вход участника;
- `/#/admin` — вход и пульт ведущего;
- `/#/screen?game=ABC234` — проектор;
- `/#/play?game=ABC234` — прямая ссылка участнику.

Если поменяли `.env`, перезапустите Vite. Локальный интерфейс подключается к настоящему Firebase из `.env`; тесты используют отдельный emulator project `demo-*`. Для участника и ведущего используйте разные профили браузера: Firebase Auth разделяет сессию между вкладками одного профиля.

```sh
npm run build
npm test
npm run test:rules
npm run test:load
```

`build` проверяет TypeScript и создаёт `dist/`. `test:rules` и `test:load` автоматически запускают и останавливают локальный Realtime Database emulator на порту 9000. Первый запуск скачивает Java emulator и требует интернета. При занятом порте остановите другой emulator. Тесты используют подставленные Firebase Auth claims только в emulator; в production используется настоящий Firebase Auth SDK.

## 6. GitHub Pages

1. Создайте пустой GitHub-репозиторий, например `red-vs-blue`. Загружайте **содержимое этой папки**, чтобы `package.json` и `.github` были в корне репозитория.
2. В **Settings → Secrets and variables → Actions → Variables** добавьте все пять `VITE_FIREBASE_*` переменных с теми же значениями, что в `.env`. Это публичная конфигурация, допустимы repository variables. Не загружайте сам `.env`.
3. В **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**.
4. Если вы ещё не используете Git в этой папке:

```sh
git init -b main
git add .
git commit -m "Build RED vs BLUE multiplayer game"
git remote add origin https://github.com/USERNAME/red-vs-blue.git
git push -u origin main
```

Замените USERNAME своим именем. Для доступа к GitHub используйте поддерживаемый GitHub способ входа (GitHub CLI, credential manager или SSH), не пароль аккаунта в URL.

5. Дождитесь зелёного workflow **Проверка и публикация** во вкладке Actions. Он устанавливает зависимости через lockfile, запускает unit/rules tests, собирает приложение и публикует `dist`.
6. Откройте `https://USERNAME.github.io/red-vs-blue/#/admin`. При изменении Firebase variables повторно запустите workflow: они встраиваются во время сборки.

Vite использует относительный `base: './'`, а маршруты находятся после `#`. Поэтому и корень домена, и путь репозитория работают без серверных rewrite/404 hacks. Прямой путь `/admin` без `#` не поддерживается GitHub Pages. QR-код строится из фактического origin и pathname.

## 7. Игра в новом формате

1. Войдите на `#/admin`, создайте игру и настройте вопросы. Старую игру предварительно обновите по [MIGRATION.md](MIGRATION.md): код, вопросы и никнеймы сохраняются.
2. Откройте экран для проектора. Участники сканируют QR-код, вводят никнейм и ждут ведущего.
3. **Начать раунд 1** — участники выражают личное мнение. После ответа кнопки блокируются, баллов за мнение нет.
4. **Закрыть раунд 1 → Начать раунд 2** — на том же вопросе участники угадывают большинство. Предыдущий ответ не мешает сделать новый прогноз, распределение голосов пока скрыто.
5. **Закрыть раунд 2 → Начислить баллы и показать результаты** — пульт последовательно готовит защищённые строки рейтинга. Прогресс отображается; после сбоя можно продолжить. Результат публикуется только после обработки всех участников.
6. За верный прогноз второго этапа — +1, за неверный или отсутствующий — +0. Ничья в первом этапе даёт +1 всем сделавшим прогноз; ноль голосов в первом этапе — +0 всем.
7. На результатах видны обе диаграммы, правильный вариант, личные баллы и рейтинг. В пульте есть отдельная вкладка рейтинга, на проекторе — топ-10.
8. Откройте следующий вопрос. Один question ID используется один раз до сброса игры.
9. **Завершить игру · Финальный рейтинг** показывает итоговую таблицу с выделением топ-3. Сброс доступен только после завершения и требует подтверждения; он очищает новый рейтинг и голоса, сохраняя вопросы, код и участников.

## Архитектура и безопасность

Подробная схема v2, доказательство проверки начислений правилами, миграция и ограничения описаны в [MIGRATION.md](MIGRATION.md).

Фазы: `waiting → phase1_open → phase1_closed → phase2_open → phase2_closed → results_revealed → phase1_open … → finished`. Firebase — источник истины; допустимость переходов проверяется сервером. Снимок вопроса остаётся одинаковым на обоих этапах.

Два набора голосов хранятся отдельно: `phase1Votes/{roundId}` и `phase2Votes/{roundId}`. Запись голоса и счётчиков атомарна; правила не разрешают подменить UID, изменить ответ, проголосовать в закрытом/старом этапе или сфальсифицировать счётчики. Участники никогда не скачивают весь список голосов. После раскрытия загружаются только проверенная сводка и опубликованный рейтинг.

Баллы не доверяются браузеру ведущего. Он предлагает детерминированные значения, а RTDB Security Rules проверяют каждый балл относительно неизменяемых голосов и предыдущего итога. Журнал обработки не позволяет пропустить участника или повторить начисление. Указатель опубликованной версии рейтинга переключается атомарно с раскрытием результатов. Cloud Functions, Blaze и новый платный backend не требуются.

Присутствие по-прежнему использует `.info/connected` и `onDisconnect()`, отдельную запись на вкладку. Человек с несколькими вкладками считается одним подключённым UID. Регистрация сохраняется при временном отключении. Счётчики ответов на проекторе обновляет открытый пульт; итоговые баллы от них не зависят.

## Ограничения и репетиция

- Один голос гарантирован на UID на этап, а не на физического человека. Другое устройство, браузер или очистка данных могут создать новый UID.
- Firebase Spark допускает 100 одновременных RTDB-соединений; 60 телефонов + пульт + проектор помещаются в этот предел. Учитывайте дополнительные вкладки и [актуальные лимиты](https://firebase.google.com/docs/database/usage/limits), [трафик и хранение](https://firebase.google.com/pricing), [Auth quotas](https://firebase.google.com/docs/auth/limits).
- На общей Wi-Fi сети заранее проверьте создание анонимных аккаунтов с одного IP. Не используйте production для массовой генерации тестовых учётных записей.
- Начисление выполняется подтверждёнными последовательными записями. На удалённой сети подсчёт 60 участников может занять десятки секунд. Пульт показывает прогресс; после reconnect или перезагрузки другой ведущий может продолжить.
- На время `phase2_closed` новые регистрации приостановлены, чтобы список для подсчёта был неизменяемым. Поздний участник после раскрытия появится в рейтинге со следующего завершённого вопроса.
- Веб SDK не сохраняет неподтверждённые offline-голоса между перезагрузками. Подтверждение показывается только после серверного принятия. Принятые ответы и UID восстанавливаются при обновлении страницы.
- Firebase Console/IAM обходит правила. Не редактируйте вручную счётчики, связи списка участников или баллы во время мероприятия. Не заявляется защита от владельца инфраструктуры.

## Тесты

```sh
npm test
npm run test:rules
npm run test:load
npm run build
```

Unit tests проверяют оба распределения, округление, переходы, начисление, ничьи, пустой первый этап и сортировку. Emulator tests покрывают авторизацию, неизменяемость голосов, защищённые счётчики, невозможность подделки баллов даже ведущим, возобновление частичного подсчёта, повторную финализацию, накопление за несколько вопросов, reconnect, reset и миграцию.

Нагрузочный тест использует 60 независимых SDK-клиентов: одновременную регистрацию, два этапа голосования, получение всех переходов, 38/22 мнения, 45/15 прогнозы, 45 верных предсказаний и одинаковый итог для всех клиентов. Фактические результаты — в [TESTING.md](TESTING.md). Emulator не заменяет репетицию на реальных телефонах.

Перед мероприятием:

1. Подключите 60 реальных телефонов (Safari iOS, Chrome Android), пульт и проектор к сети площадки. Проверьте регистрации и online-count.
2. Проведите оба этапа с заранее известным распределением; убедитесь, что между ними нет процентов или чужих голосов. Проверьте возможность поменять цвет между этапами и невозможность поменять уже принятый ответ внутри этапа.
3. Измерьте задержку переходов, подтверждения ответа и полного начисления баллов. Сохраните p50/p95/max, ошибки, модели телефонов и сведения о Wi-Fi.
4. Перезагрузите телефоны после первого и после второго ответа; отключите сеть на нескольких устройствах перед закрытием этапа. Поздние записи должны отклоняться.
5. Во время подсчёта перезагрузите пульт и нажмите продолжение. Баллы не должны дублироваться; частичный рейтинг не должен появляться у участников.
6. Проверьте ничью, ноль голосов в первом этапе, пропуск прогноза, накопление за несколько вопросов, финальный рейтинг и подтверждение сброса.
7. Проверьте соединения и трафик в Firebase Usage. Перед основной игрой устраните ошибки и повторите репетицию.

### Локальные emulators для браузера

Для разработки используйте `.env.local` с demo-проектом `demo-red-blue`: API key `demo-key`, app ID `demo-app`, auth domain `demo-red-blue.firebaseapp.com`, database URL `https://demo-red-blue-default-rtdb.firebaseio.com`, `VITE_USE_EMULATORS=true`. Запустите `npx firebase emulators:start --project demo-red-blue --only auth,database`, затем в другом терминале `npm run dev`. Auth работает на 9099, RTDB на 9000. Режим действует только при `import.meta.env.DEV`; production использует реальную конфигурацию. Для автоматических тестов `.env` не требуется.
