# Обновление действующей игры: два этапа и рейтинг

Изменения выполнены в существующем репозитории `vmirkvss/red-vs-blue`, ветка `feature/two-phase-voting`. Хостинг, Firebase-проект `redblue-76c60`, `.env`, Authentication, allowlist и URL игры сохраняются. Платные сервисы и Cloud Functions не добавлены.

## Порядок публикации

Новые правила и новый frontend несовместимы со старым игровым протоколом. Выполняйте обновление **между мероприятиями**. Нельзя сначала опубликовать frontend и оставить старые правила: запись голосов будет отклоняться.

1. Завершите текущую игру старым пультом. Попросите участников закрыть вкладки до окончания обновления.
2. В Firebase Console → Realtime Database → Data → меню **Export JSON** сохраните резервную копию. На вкладке Rules также сохраните копию прежних правил. Не добавляйте экспорт с данными участников в публичный репозиторий.
3. В **Realtime Database → Rules** замените правила содержимым актуального `database.rules.json` этой ветки и нажмите **Publish**. Allowlist `/admins` менять не требуется.

   Альтернатива через CLI, из папки проекта:

   ```sh
   npx firebase login
   npx firebase deploy --only database --project redblue-76c60
   ```

4. После обновления правил объедините PR ветки `feature/two-phase-voting` в `main`. GitHub Actions запустит unit, rules и 60-client tests, затем сборку и GitHub Pages deploy. PR-проверки сами ничего не публикуют.
5. После успешного deploy откройте `https://vmirkvss.github.io/red-vs-blue/#/admin` и обновите страницу. Войдите прежним аккаунтом.
6. Создайте новую игру **или** откройте прежний код. Для старой игры пульт покажет предложение обновления: нажмите **Подготовить обновление → Подтвердить обновление**. Это атомарная миграция конкретной игры.
7. Проверьте короткий раунд с двумя браузерами, затем попросите всех участников обновить страницы. Закэшированный старый клиент не может писать по новому протоколу.

Firebase CLI в среде разработки сейчас не имеет авторизованного аккаунта. Поэтому новые правила production-базы не публиковались, ветка `main` и действующий сайт оставлены без изменений. Для запуска нужна операция из пункта 3, затем merge PR. Пароль Firebase передавать в чат не нужно.

## Что сохраняется и что меняется

- Код игры, вопросы (включая порядок и IDs), UID и никнеймы сохраняются.
- Прежние `/votes` остаются read-only архивом для администратора. Они не превращаются в баллы: в старой версии не было прогнозов.
- Состояние становится `schemaVersion: 2`, фаза `waiting`. Рейтинг нового формата начинается с нуля.
- В профиль добавляется служебная ссылка `next`; рядом создаётся `roster` со списком участников. Для существующих данных это единственная операция, где авторизованный ведущий задаёт начальный список. После миграции порядок списка и его полнота защищены правилами.
- Повторная миграция уже обновлённой игры отклоняется. Пользовательский reset доступен только после завершения и с подтверждением; он удаляет голоса нового формата, результаты и баллы, но сохраняет вопросы и профили.
- Копии прежних игр не удаляются. Самостоятельно удалять `roster`, `scoringStatus`, отдельные голоса или строки рейтинга в Console во время игры нельзя: Console/IAM обходит Security Rules и может нарушить целостность.

## Новый сценарий ведущего

`waiting → phase1_open → phase1_closed → phase2_open → phase2_closed → results_revealed → phase1_open … → finished`

1. **Начать раунд 1**: личное мнение, без баллов.
2. **Закрыть раунд 1**.
3. **Начать раунд 2 · Угадай большинство**: тот же вопрос, новый неизменяемый голос.
4. **Закрыть раунд 2**.
5. **Начислить баллы и показать результаты**. Дождитесь завершения обработки всех участников. До завершения распределения и новый рейтинг скрыты.
6. Откройте следующий вопрос или **Завершить игру · Финальный рейтинг**.

Каждый question ID можно открыть один раз до reset. Кнопки не позволяют пропустить этап; прямой API-запрос также отклоняется правилами. Для аварийной остановки закрывайте текущий этап и доводите вопрос до результатов. Завершить игру можно из ожидания или после раскрытия.

## Начисление без платного backend

Клиент ведущего предлагает записи, **но не определяет допустимость начисления**:

- Голос и два счётчика обновляются атомарно. Правила проверяют, что ровно один счётчик увеличился на 1 вместе с новым голосом текущего UID. Подмена счётчиков или запись без них невозможна, в том числе ведущим.
- После `phase2_closed` оба набора голосов неизменяемы. Новые регистрации на время подсчёта закрыты.
- `/scoringStatus/{roundId}` хранит указатель на следующего участника и количество обработанных. Обработка идёт по неизменяемому списку `participants/{uid}/next`. Правила не разрешают перескочить через участника.
- Каждая строка `scores/{roundId}/{uid}` создаётся один раз, одновременно с продвижением указателя. Правила самостоятельно сравнивают прогноз с защищёнными счётчиками первого этапа, проверяют +0/+1 и прибавление к предыдущему опубликованному итогу.
- При ничьей получают +1 все сделавшие прогноз. При отсутствии голосов в первом этапе никто не получает баллов. Отсутствующий прогноз даёт +0.
- Когда обработан весь список, одной atomic update публикуются проверенный `roundResults` и `state.scoreVersion`, а фаза становится `results_revealed`. Частичный рейтинг недоступен участникам.
- После сбоя ведущий нажимает **Продолжить подсчёт и показать результаты**. Уже созданные строки не изменяются и баллы не дублируются. Другой авторизованный ведущий может продолжить тот же журнал.

Это использование доверенного механизма **серверных RTDB Security Rules**, а не доверие браузерному расчёту. Тесты отдельно доказывают отказ неверному начислению даже от allowlisted host. Cloud Functions/Blaze не требуются.

Ограничения: ведущий должен держать пульт открытым до окончания подсчёта; 60 последовательных подтверждённых записей на удалённой сети могут занимать десятки секунд. Без открытого пульта автоматический подсчёт в фоне не запускается, но его всегда можно продолжить. Firebase Console, Admin SDK и владелец IAM могут обходить правила; защита от владельца инфраструктуры не заявляется. Сохраняется ограничение «один голос на UID», а не на человека.

## Схема v2

```
games/{code}/state                           # schemaVersion, phase, roundId, scoreVersion, question
games/{code}/questions/{questionId}          # прежний сценарий
games/{code}/participants/{uid}              # name, next
games/{code}/roster                          # head, count
games/{code}/presence/{uid}/{connectionId}    # прежняя online-presence
games/{code}/phase1Votes/{roundId}/votes/{uid}
games/{code}/phase1Votes/{roundId}/counts     # red, blue
games/{code}/phase2Votes/{roundId}/votes/{uid}
games/{code}/phase2Votes/{roundId}/counts
games/{code}/scores/{roundId}/{uid}           # name, total, correct, completed, earned
games/{code}/scoringStatus/{roundId}          # cursor, processed
games/{code}/roundResults/{roundId}           # phase1, phase2, winner, awarded
games/{code}/usedQuestions/{questionId}       # roundId
games/{code}/tally                           # roundId, phase1 total, phase2 total
games/{code}/votes                           # read-only архив старой версии
```

`roundId` — уникальный экземпляр вопроса; его исходный question ID хранится в снимке состояния. Версии `scores` позволяют восстановить итоги без суммирования инкрементов при повторном запросе. `state.scoreVersion` указывает на опубликованную версию. Поле `completed` — количество сделанных прогнозов второго этапа; `correct` — количество верных прогнозов.

Участники не скачивают чужие сырые голоса даже после раскрытия. Им доступны только свои записи, проверенная сводка текущего опубликованного вопроса и опубликованный рейтинг. Во время голосования пульт слушает два узла `counts`; проектор получает только общие числа ответивших через `tally`. Счётчик проектора может запаздывать при закрытом пульте; начисление от него не зависит.

Порядок рейтинга: баллы по убыванию → выполненные прогнозы по убыванию → имя по русскому алфавиту; при полностью совпадающих именах применяется стабильный порядок UID. Время ответа не используется. На итогах участник выделен в таблице, проектор показывает топ-10, финальная таблица содержит всех и выделяет первые три места.

## Восстановление и проверка

До публикации: `npm run build`, `npm test`, `npm run test:rules`, `npm run test:load`.
Правила генерируются из комментированного `scripts/generate_rules.py`: `npm run rules:generate`. После изменения генератора обязательно снова запускайте rules и load tests; в Console публикуется именно сгенерированный JSON.

При проблемах после публикации не редактируйте баллы вручную. Сохраните экспорт базы и текст ошибки. Если ошибка только в соединении/пульте, повторите финализацию. Для отката всего протокола потребуются согласованная прежняя версия frontend, прежние правила и состояние из резервной копии; такой откат выполняется в отдельное окно обслуживания. Не накатывайте старую резервную копию поверх уже сыгранных новых вопросов без сохранения новых данных.
